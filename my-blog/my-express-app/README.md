# Blog API (Express + Prisma + PostgreSQL)

## Структура

```
src/
  app.ts            # збирає Express-застосунок (без listen) — його ж їдять тести
  server.ts         # точка входу: піднімає порт
  lib/prisma.ts     # єдиний інстанс PrismaClient (зручно мокати)
  lib/cache.ts      # кеш-шар на Redis
  routes/           # опис ендпоінтів
  controllers/      # логіка
  middlewares/      # перевірка JWT
tests/
  unit/             # юніт-тести: Prisma замокана, база не потрібна
  integration/      # інтеграційні: справжній HTTP + справжній PostgreSQL
```

## Валідація вхідних даних

Усе, що приходить від клієнта, перевіряється схемами `zod`
(`src/schemas/`) через middleware `validate(schema, source)`.
База стежить за типами й звʼязками, але їй байдуже до порожнього
заголовка чи пароля з трьох символів — це робота застосунку.

При помилці — `400` зі списком полів, щоб форма підсвітила
конкретний інпут:

```json
{
  "error": "Некоректні дані",
  "details": [{ "field": "password", "message": "Пароль має бути щонайменше 8 символів" }]
}
```

Порядок middleware у роутах навмисний: спершу `authMiddleware`
(`401` — «хто ти»), і лише потім `validate` (`400` — «що прислав»).
Неавторизований користувач не має дізнаватись деталі схеми.

Middleware ще й приводить типи: `?page=2` у контролер приходить
числом, `postId` з форми — теж. Невідомі поля просто відкидаються,
тому `authorId` із тіла запиту не має шансів підмінити автора.

## Пагінація

`GET /api/posts` віддає `{ data, meta }`:

```json
{
  "data": [ ... ],
  "meta": { "page": 1, "limit": 10, "total": 25, "totalPages": 3 }
}
```

За замовчуванням 10 постів, `limit` обмежений 50 — без верхньої межі
`?limit=1000000` обходив би пагінацію й вивантажував усю базу одним
запитом.

## Кешування (Redis)

Стратегія — **cache-aside**: контролер спершу питає Redis, при промаху
йде в PostgreSQL і кладе результат назад у кеш.

| Ключ | Що тримає | TTL |
| --- | --- | --- |
| `posts:list:v{версія}:p{сторінка}:l{limit}` | одна сторінка `GET /api/posts` | 60 с |
| `post:{id}` | відповідь `GET /api/posts/:id` разом з коментарями | 60 с |

**Чому у ключі списку є версія.** З пагінацією кеш списку — це не один
ключ, а по ключу на кожну комбінацію сторінки й розміру. Видаляти їх
поштучно неможливо, а бігати по базі через `KEYS`/`SCAN` на кожен новий
пост — дорого. Тому номер версії вшито в ключ: щоб знецінити всі
сторінки одразу, достатньо `INCR` — старі ключі стають недосяжними й
помирають за TTL.

Кожна відповідь на ці два роути має заголовок `X-Cache: HIT` або `MISS` —
зручно перевіряти руками через `curl -D -`.

**Інвалідація** — явна, одразу після зміни даних:

| Дія | Що скидається |
| --- | --- |
| створення поста | версія списку `+1` (усі сторінки) |
| оновлення / видалення поста | версія списку `+1` + `post:{id}` |
| створення / зміна / видалення коментаря | `post:{postId}` |

Коментар навмисно не чіпає кеш списку: у списку коментарів немає,
тож він від нового коментаря не застаріває.

TTL при цьому лишається як страхувальна сітка: якщо десь забули
інвалідувати, дані застаріють максимум на хвилину.

### Два принципи, на яких тримається цей шар

1. **Redis не є критичною залежністю.** Усі операції кешу обгорнуті в
   `try/catch`: якщо Redis лежить, `cacheGet` повертає `null`, і запит
   просто йде в базу. Перевірено — з погашеним Redis API віддає `200`,
   а `/api/health` показує `cache: "down"` при `status: "ok"`.
2. **404 не кешується.** Інакше щойно створений пост «не існував би»
   ще цілу хвилину.

Без змінної `REDIS_URL` кеш просто вимикається — так працюють юніт-тести
й локальний запуск без Docker.

## Зображення: R2 / MinIO

Картинки лежать в об'єктному сховищі, а не в базі — у PostgreSQL
тільки метадані (`Media`: ключ, URL, тип, розмір, автор).

Локально працює **MinIO** з `docker-compose.yml`: те саме S3 API, що й
у Cloudflare R2, тому код однаковий, а акаунт і картка не потрібні.
Вебконсоль сховища — http://localhost:9001 (minioadmin / minioadmin).

| Роут | Дія |
| --- | --- |
| `POST /api/media` | завантажити зображення (multipart, поле `file`) |
| `DELETE /api/media/:id` | видалити (тільки той, хто завантажив) |

Пост має необов'язкову обкладинку: `imageId` у `POST`/`PUT /api/posts`.
`null` прибирає її. Прикріпити чужу картинку не можна — `403`.

### Що тут захищено

1. **Тип файлу визначається за вмістом**, а не за заголовком
   `Content-Type`: його присилає клієнт, тобто `.sh` легко віддати як
   `image/png`. Перевіряємо магічні байти (JPEG/PNG/WebP/GIF).
2. **Ім'я файлу від користувача не використовується** — ключ
   генерується як `images/РІК/МІСЯЦЬ/uuid.ext`. Інакше `../../etc/passwd`
   або перезапис чужого файлу однаковим іменем.
3. **Ліміт 5 МБ** на рівні multer — запит обривається, не дочитуючись.
4. При видаленні `Media` файл прибирається і зі сховища, а пост
   лишається живим (`onDelete: SetNull`), просто без обкладинки.

### Перехід на справжній Cloudflare R2

Код міняти не треба — тільки змінні середовища в `docker-compose.yml`:

```yaml
S3_ENDPOINT: 'https://<account_id>.r2.cloudflarestorage.com'
S3_BUCKET: '<назва бакета>'
S3_ACCESS_KEY_ID: '<з панелі R2>'
S3_SECRET_ACCESS_KEY: '<з панелі R2>'
S3_PUBLIC_URL: 'https://pub-<hash>.r2.dev'
```

Кроки в панелі Cloudflare: R2 → Create bucket → Settings → Public
access увімкнути (або підключити власний домен) → Manage API Tokens →
створити токен з правами Object Read & Write. Після цього сервіси
`minio` і `minio-init` з compose можна прибрати.

Без `S3_*` змінних сховище просто вимкнене: завантаження відповідає
`503`, решта блогу працює як і раніше.

## Тести

### Юніт-тести

Prisma й Redis повністю замокані, тому контейнери не потрібні — тести
йдуть за секунди. Перевіряють логіку контролерів і middleware: хешування
пароля, payload JWT, права доступу (403 для чужих постів/коментарів),
404, обробку помилок, схеми валідації та поведінку кешу (включно з тим,
що на HIT база не смикається взагалі).

```bash
npm test
```

З покриттям:

```bash
npm run test:coverage
```

### Інтеграційні тести

Піднімають увесь застосунок через `supertest` і ходять у справжні
PostgreSQL та Redis з `docker-compose.test.yml` (окрема база `blog_test`
на порту 5433, Redis на 6380, дані в tmpfs). Перевіряють повні сценарії:
реєстрація → логін → CRUD постів → CRUD коментарів, включно з каскадним
видаленням, пагінацією, валідацією та інвалідацією кешу.

```bash
npm run test:integration
```

Скрипт сам підніме контейнер з базою і накотить міграції. Прибрати базу
після роботи:

```bash
npm run test:db:down
```

### Все разом

```bash
npm run test:all
```

## CI

`.github/workflows/my-blog-ci.yml` ганяє все це на кожен push і PR,
що зачіпає `my-blog/`: типи, юніт- та інтеграційні тести (PostgreSQL і
Redis піднімаються як service-контейнери на тих самих портах, що
локально), лінт і збірку фронтенду, плюс `nginx -t` на конфіг.

## PostgreSQL 18

Проєкт працює на `postgres:18-alpine`. Дві речі, які ламаються при
наївному оновленні тега з 15 на 18:

**1. Змінилась тека даних.** У образах 18+ дані лежать у
`/var/lib/postgresql/<версія>/docker`, а не в `/var/lib/postgresql/data`.
Тому том монтується на рівень вище:

```yaml
volumes:
  - pgdata18:/var/lib/postgresql   # було pgdata:/var/lib/postgresql/data
```

Зі старим монтуванням сервер не стартує взагалі — пише, що знайшов
дані в «unused mount/volume».

**2. Формат даних несумісний між мажорними версіями.** Том від 15-ї
не відкриється під 18-ю: потрібен `pg_upgrade` або дамп/відновлення.
Тому в compose навмисно новий том `pgdata18` — старий `pgdata`
лишається на диску недоторканим.

### Перенести дані зі старого тому

Робиться до оновлення тега, поки ще запущена 15-та версія:

```bash
# 1. Дамп зі старої бази
docker compose exec -T postgres pg_dump -U postgres -d blog --clean --if-exists > blog.sql

# 2. Оновити compose (образ + точка монтування + назва тому), потім:
docker compose up -d postgres

# 3. Залити дамп у нову
docker compose exec -T postgres psql -U postgres -d blog < blog.sql
```

Перевірено на цьому проєкті: перенесення проходить без жодної помилки.

Коли старий том більше не потрібен:

```bash
docker volume rm my-blog_pgdata
```
